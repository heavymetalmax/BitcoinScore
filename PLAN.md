# BitcoinScore — План робіт

## Головне правило
**Єдина база даних** → `data/history/scores.json`  
Все що показується на сайті береться звідти і тільки звідти.

## Карта системи (поточний стан)

```
unified_history.json  ←── єдине джерело метрик для перерахунку
        ↓
recompute_backtest.py ←── будує scores.json з V3 методикою
        ↓
scores.json           ←── ЄДИНА БАЗА (3850 записів)
   ├── backfill_v2 (731) ← 2016-2017, стара методологія
   ├── recompute_v3 (2647) ← 2018-2025-03, V3 але проблемний нормалайзер
   └── live (472) ← 2025-04+, живий скрейпер
        ↓
export_web.py → web/ → GitHub Pages
```

## Відомі проблеми (пріоритет)

### 🔴 П1 — Нормалізатор: path-dependence
**Симптом:** Double Top 2021 ($69k) → score 76, але Spring ATH ($63k) → score 88.  
Той самий рівень ціни = різний ризик залежно від шляху.  
**Причина:** 4-річне ковзне вікно скидає baseline після корекції.  
**Рішення:** Ratchet normalization — percentile baseline може тільки рости.

### 🟡 П2 — backfill_v2 (2016-2017): стара методологія
**Симптом:** 731 запис в базі з іншого алгоритму (source=backfill_v2).  
**Рішення:** Перерахувати ці дати з V3+ratchet або чесно позначити як "обмежені дані".

### 🟡 П3 — unified_history.json: unit bugs у першоджерелі
**Симптом:** nupl зберігається як частка (0.48), asopr як delta (0.005).  
Recompute_backtest фіксує це на льоту, але першоджерело брудне.  
**Рішення:** Виправити безпосередньо в unified_history.json + задокументувати формат.

### 🟠 П4 — Паралельні версії scoring
**Симптом:** scoring.py, scoring_v2.py, scoring_v3.py, score.py — незрозуміло що активне.  
**Рішення:** Задокументувати яка версія є канонічною. Решта — архів або видалити.
